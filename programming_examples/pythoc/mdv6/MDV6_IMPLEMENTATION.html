This document describes how a YOLOv9-c–class object detector is compiled and executed on the AMD XDNA2 (NPU2 / AIE2P) spatial array. It covers the network topology, the hardware substrate, how each layer is decomposed into NPU dispatches, how Conv+BN+SiLU is fused into single on-core kernels, how the 32 cores are laid out spatially and scheduled in time, how data and weights move between DDR / memtile L2 / core L1, and where the frame time actually goes. The recurring theme: this model is dispatch/host-bound, not compute-bound — the arithmetic is <0.1% of peak, and almost every optimization in the codebase is about collapsing launches, not making math faster.

1 · The network — YOLOv9-c / GELAN

MDV6 is Microsoft CameraTraps' MegaDetector v6, an MIT-licensed YOLOv9-c wildlife detector with 3 classes (animal / person / vehicle). The architecture is GELAN: a backbone of ELAN and RepNCSPELAN blocks, an SPPELAN + FPN/PAN neck, and a 3-scale detection head (P3 80×80, P4 40×40, P5 20×20). Channel progression is 32→64→128→192→256.

Fig 1. Full MDV6 dataflow. Blue = ELAN/RepNCSPELAN blocks (the bulk of compute), amber = neck, violet = head. Skip connections B3/B4/N3/N4 are concatenated downstream (FPN top-down then PAN bottom-up).

1.1 · The building blocks

Conv (the atom)

SiLU(BN(Conv2d(x))) — every convolution in the model. Bias-free conv, BatchNorm (eps 1e-3), SiLU activation. At inference BN folds into the conv weights, so the NPU kernel sees a single packed weight blob and applies BN as a per-output-channel scale+bias before SiLU.

AConv (downsample)

Conv3×3,s2( AvgPool2×2,s1(x) ). The 2×2 average-pool runs on the CPU; the strided 3×3 conv runs on the NPU. Used at every resolution drop (aconv3/5/7/16/19).

RepConv (reparameterized)

At train time SiLU(BN(3×3) + BN(1×1)); at inference the 1×1 branch folds into the center tap of the 3×3 kernel and both BNs collapse into one. fuse_repconv() does this on the host so a single packed 3×3 conv kernel runs it — no separate 1×1 dispatch.

ELAN / RepNCSPELAN

conv1 (1×1) splits channels into x1/x2; two processing branches (conv2,conv3 — each a RepNCSP + 3×3 in the Rep variant); then conv4 (1×1) fuses cat[x1,x2,x3,x4]. This 4-way concat is the GELAN "aggregation". 9 RepNCSPELAN blocks dominate the model.

RepNCSP / Bottleneck

conv1,conv2 (1×1) on the same input; a stack of repeat_num=3 Bottlenecks (each = RepConv 3×3 → Conv 3×3 → +residual); then conv3 (1×1) over cat. The bottleneck stack is exactly what the rn3 halo chain fuses into one launch.

SPPELAN

conv1 (1×1) then three cascaded MaxPool 5×5,s1 (run on CPU); concat all four, then conv5 (1×1). Spatial-pyramid pooling at the deepest scale (20×20).

2 · The hardware — NPU2 / AIE2P array

The target is the AMD XDNA2 NPU (aie.device(npu2), AIE2P generation). The compute fabric is an 8-column × 4-row grid of 32 VLIW AI-Engine cores, fronted by a row of memtiles (L2 scratch) and a row of shim tiles (the DDR/NoC boundary). Data flows vertically: DDR → shim → memtile L2 → core L1, compute, then back down.

Fig 2. NPU2 substrate. The conv/GEMM designs treat each column independently: a column's shim pulls that column's slice of the input from DDR, the memtile splits it to 4 cores, cores compute, the memtile joins 4 outputs and the shim writes them back.

3 · Mapping the network onto the array

The host (test_full_model_mc.py) runs the PyTorch module graph but replaces every Conv+BN+SiLU with a call into the NPU dispatch engine (run_tiled_mc.py). The model is executed layer-by-layer, sequentially — there is no cross-layer pipelining on the array. Each NPU layer is one or a few xrt.run launches; the glue (pooling, upsample, concat, residual add, detection) stays on the CPU. Activations round-trip through DDR between layers.

3.1 · What runs where

On the NPU (32 cores)

  • All 3×3 convs → conv3x3_fused_packed_bf16
  • All 1×1 convs → GEMM path (gemm_conv1x1_*)
  • RepConv bottleneck convs (folded to 3×3)
  • The rn3 bottleneck stacks (chain, incl. residual+SiLU)

On the CPU (host)

  • AvgPool (AConv), MaxPool (SPPELAN), Upsample
  • All concat / split / chunk (channel slicing, np.concatenate)
  • Per-iteration residual add when not using the chain
  • The Detection head: anchor/class convs, softmax, anc2vec/DFL
np.concatenate alone fires ~1300 times/frame (≈9 ms). It is cheap per-call but a symptom: the HWC channel layout means every GELAN aggregation and skip-connection is a host-side memory shuffle between NPU launches.

4 · Kernel fusion — Conv+BN+SiLU in one call

There are exactly four PythoC-compiled compute kernels (one .o set in kernels/build/), plus the BFP576 chain kernels. Fusion happens at two levels: op-fusion (BN and SiLU are computed inside the conv kernel, no host round-trip), and weight-fusion (RepConv's two branches and BatchNorm collapse into the conv weights on the host).

4.1 · The 3×3 conv inner loop

The kernel walks output channel-blocks of 8, computes 4 output pixels at a time via a mmul<4,8,8> (4 pixels × 8 IC × 8 OC), reducing over IC-blocks × 9 kernel taps, then applies BN (per-OC scale+bias) and a polynomial SiLU before storing. Crucially, the weights arrive pre-packed so the inner loop is a contiguous load_v<64> per tap.

Weight packing for mmul<4,8,8>

PyTorch OIHW weights [OC,IC,3,3] are repacked on the host (cached by weight id) into [OC/8, IC/8, 9, 8ic, 8oc] — the exact order the inner loop streams. BN scale/bias are appended as 2·OC bf16 values. So one weight BO = packed conv + BN, and the kernel reads it linearly.

conv block  [OC, IC, 9]
  → [OC/8, 8, IC/8, 8, 9]
  → permute (OC/8, IC/8, 9, 8ic, 8oc)
  → flatten  ++ bn_w[OC] ++ bn_b[OC]

1×1 GEMM uses [IC/8, OC/8, 8ic, 8oc]; K-blocked appends BN to each K-chunk but only applies it on the final chunk. Channels are always padded to multiples of 8 (and IC=3 stem padded to 8).

4.2 · Weight-level fusion — RepConv & BatchNorm

fuse_bn() folds BatchNorm into conv weights at model load (prewarmed once, id-keyed cache). fuse_repconv() goes further: it collapses RepConv's parallel BN(3×3) + BN(1×1) into a single 3×3 kernel by adding the 1×1 weights into the center tap and merging both BN affines, setting bn_w=1 so the standard 3×3 kernel runs it verbatim. This moved RepConv off the CPU and removed a whole class of host work and an extra dispatch per bottleneck.

5 · Spatial layout — 32 cores, split / join / broadcast

A conv layer's output is tiled into fixed tile_h × tile_w output tiles. Each tile (plus its halo) is a "patch". The 32 cores each process patches_per_core patches per invocation. The IRON generator (aie2_multicore.py) builds a per-column dataflow: a bulk input ObjectFifo is split at the memtile into 4 per-core patch FIFOs, the weight blob is broadcast to all 4 cores, and 4 per-core outputs are joined back at the memtile for the shim to drain.

Fig 3. Per-column dataflow. Blue = input fan-out (split), amber = weight broadcast, green = output fan-in (join). All eight columns run this identically and independently; the host fills/drains each column with a strided TensorAccessPattern.

5.1 · How patches are distributed

The host slices the output grid into tiles_h × tiles_w tiles, builds a patch (tile + halo) per tile, and packs them as core 0: patches[0..ppc-1], core 1: patches[ppc..2·ppc-1], … across 32 cores. If a layer has more tiles than 32 × ppc, the host loops in spatial batches (each a separate sub-run); short batches are padded by repeating patch 0. After the run, output tiles are reassembled to the spatial grid via the inverse index (core·ppc + slot).

5.2 · RTPs — one ELF, many shapes

Six per-core int32 runtime parameters (tile_h, tile_w, ic, oc, stride, padding) are written by the host each dispatch. This lets a single compiled ELF/ObjectFifo envelope serve a whole family of layer shapes without recompiling — essential because there are dozens of distinct conv shapes but only a handful of ELFs.

6 · Dispatch mechanisms — collapsing launches

Because the frame is dispatch-bound (~2.3 ms of host plumbing per launch), the central optimization is to do more work per xrt.run. The codebase evolved a ladder of ELF formats, each one folding more host-level loops into a single NPU launch. The compiler emits one binary containing N device blocks plus a dispatcher device; the dispatcher's @main issues aiex.configure { aiex.run … } per sub-device, sequentially.

Net effect across all phases: 453 → 84 launches/frame. Sub-runs within one xrt.run are sequential on the array (they take turns, not parallel), but they amortize the per-launch host gap — which is the dominant cost.

6.1 · The dispatcher stitching (MLIR shape)

module {
  aie.device(npu2) @sub0_mc_re6_c3 { /* cores, memtiles, ObjectFifos, runtime_sequence */ }
  aie.device(npu2) @sub1_...       { ... }
  aie.device(npu2) @main_dispatcher {
    aie.runtime_sequence @main(%w, %in, %out, ...) {
      aiex.configure @sub0_mc_re6_c3 { aiex.run @sub0_..._seq(%in, %w, %out) }
      // more configure/run pairs for clones / pairs / OCB iterations
    }
  }
}

share_arg_idxs={1} promotes each sub's weight arg to a shared dispatcher arg; chain_links=[(src_sub,src_arg,dst_sub,dst_arg)] aliases one sub's input to another's (the GEMM-pair trick). BD slots reset between sub-devices.

BOs are pooled per (elf, role, size) and reused; prepared xrt.run objects are cached by (kernel-id, arg-ids) so steady-state launches skip set-up. Only the consumed byte range is synced to/from device each call.

7 · The rn3 halo chain — N bottlenecks, one launch

The RepNCSP bottleneck stack is repeat_num=3 iterations of x ← x + Conv3×3( RepConv3×3(x) ) — six 3×3 convs plus residual adds, in strict sequence. Naively that is 6+ launches and 3 host residual adds per stack, repeated at re4 (80²), re6 (40²), re8 (20²) and again in the neck/head. The halo chain fuses an entire stack into one launch, keeping activations resident on-chip and applying the residual+SiLU inside the kernel.

Fig 4. The chain alternates two DDR image BOs per iteration ("halo-bounce"). conv1 → mask → conv2res(+residual+SiLU) run back-to-back on each core; the host re-streams weights and re-triggers fill/drain per iteration but never unpacks/repacks activations between iterations.

The raster path pins 1 tile/core and rasters the output grid across rounds; the geo path column-pins multiple tiles per column. re4/re6 use raster by default (MDV6_RN3RASTER=1); re8 uses geo. A "mask" kernel zeros the halo region outside the valid image before the residual add.

7.2 · Temporal schedule inside the chain

Per iteration, per pass, per tile: acquire input tile from the FIFO; loop weight-blocks doing conv1 into a scratch buffer; mask the scratch; loop output-blocks doing conv2res (3×3 over scratch, + residual from the iteration's input, + SiLU) into the output tile; release. Weights for each iteration are streamed from DDR (or replayed from L2 — §8). The residual is read from the same iteration's input buffer, so the chain must keep x_i intact while writing x_{i+1} — the reason for the two ping-pong BOs.

8 · BFP576 compute + weight replay

BFP576 hardware MAC

The default mmul<4,8,8> path is an emulated bf16 matmul (shuffle-bound, ~5.12 TFLOP/s peak). The AIE2P core also has a native BFP576 (block-floating-point, 8×8×8) MAC — 576 multipliers, shared exponent per 8-element block — that is ~5.6× denser and reaches tens of TOPS.

The chain's chain_conv1_bfp / chain_conv2res_bfp are drop-in BFP576 versions of the chain convs: they build the activation operand via on-the-fly im2col, vshuffle the pre-packed weights into BFP layout, and accumulate in a 2048-wide BFP accumulator before BN+SiLU. They are default-on (MDV6_CONV1_BFP=1, MDV6_CONV2_BFP=1).

Weight replay (wr2)

In the raster chain with TPR>1 (re4w), the same weight slots are needed every round. Replay fills the weights into the memtile once per iteration and re-emits them from L2 (~14 GB/s measured, ~8× shim BW) instead of re-reading DDR each round. Host upload drops from TPR× to 1× the weight bytes.

It is wired as MDV6_WTREPLAY2=1 (default-on, ring-buffer post-resolve patch). For re6w (TPR=1) it is a no-op; re8 geo doesn't use it.

Why these don't move the wall. Both BFP576 and weight-replay attack NPU compute and weight-DMA — but those live inside the 158 ms npu_run bucket, which is only 33% of the frame, and the chain convs are a slice of that. Measured: npu_run is 158 ms with them on, 159 ms with them off. They are kept default-on because they are correct, slightly more accurate, and harmless — not because they change throughput. The wall is set by launch count, not arithmetic.

9 · Temporal schedule — the frame timeline

A frame is a strictly sequential walk of the layer graph. There is no overlap between NPU compute and host glue, and no cross-layer pipelining: layer L's output must come back to DDR, be concat/pooled/upsampled on the CPU, and be re-uploaded before layer L+1 launches. 10 · Communication, speeds & feeds

Data movement per launch

  • Host packs patches → fills input BO → sync_to_device (only bytes written).
  • shim → memtile (one DMA per column), memtile split → 4 core L1 patch FIFOs.
  • weight BO broadcast to all 4 cores in a column (depth-1 FIFO).
  • cores compute, memtile joins 4 outputs, shim → DDR out BO.
  • host sync_from_device (only consumed bytes) → reassemble grid.

Measured bandwidths

shim DDR↔chip~1.7 GB/s / shim
memtile L2 replay~14 GB/s
per-core S2MM (replay col)~10.5 GB/s
launch plumbing~2.3 ms / launch

Weight DMA is the chain's pace-setter (~83 KB/col/round at shim BW), which is what replay targets.

11 · Where the time goes — roofline & levers

The logical work is 9.8 GMAC / 19.6 GFLOP per frame. At the bf16 emulated peak (5.12 TFLOP/s) that is a 3.83 ms compute floor (≈261 fps); the optimistic DDR floor (~50 GB/s, 156 MB) is 3.12 ms. The measured warm wall is ~479 ms — roughly 1200× the compute floor, and even the NPU-active 158 ms is ~40× over it. The model is decisively orchestration/dispatch/data-movement bound.

11.1 · The dispatch-collapse model

If the non-launch floor were ~30 ms and per-launch overhead could be driven down, throughput scales with launch count:

launches@2.3 ms/launch (today)@1.34 ms/launch@0.6 ms/launch
84 (today)~479 ms / 2.1 fps~143 ms / 7 fps~80 ms / 12 fps
50~145 ms~97 ms / 10 fps~60 ms / 17 fps
25~88 ms~64 ms / 16 fps~45 ms / 22 fps

Numbers illustrative (from the roofline note, re-based on the current 84/479 operating point). The two independent levers are fewer launches and cheaper launches.

11.2 · Remaining levers (in priority order)

  1. Cut per-launch overhead. 2.3 ms/launch is the single biggest term (40% of frame). Anything that reduces the Python/pyxrt cost per xrt.run multiplies across all 84 launches.
  2. Fuse more launches. The heavy mc_*_c3 3×3 convs run multiple times/frame; block-level fusion (a whole RepNCSPELAN stage resident) would remove host round-trips between its sub-convs.
  3. Reduce host glue. ~1300 np.concatenate/frame + CPU pool/upsample/detect; moving GELAN aggregation on-chip would cut both the numpy and the surrounding launch gaps.
  4. Weight-replay i3–i12 (producer-leg redesign) for the deep chains — bandwidth, only matters once dispatch is addressed.
Bottom line: every compute-side optimization in this codebase (BFP576, weight replay, mmul packing, RepConv fusion) is correct and shipped, but the frame is gated by how many times the host hands work to the NPU and waits. The path to 10×+ is launch-count collapse and host-glue elimination, not faster math.
